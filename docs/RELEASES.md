# Подписанные релизы Luna

> Как выпускать обновления, которые станция примет только от владельца ключа,
> и почему сборка без ключа вообще не обновляется сама.

## Зачем подпись

Автообновление скачивает бинарник с GitHub и запускает его от root. SHA-256
подтверждает только целостность файла: подменивший релиз или `SHA256SUMS`
подменит и хеш. Поэтому updater доверяет релизу только после проверки
Ed25519-подписи файла `SHA256SUMS` ключом, вшитым в бинарник при сборке.

Подпись покрывает и `manifest.json`: его хеш — отдельная строка в
`SHA256SUMS`. Версия в манифесте защищена той же подписью, поэтому старый
подписанный релиз нельзя подсунуть поверх нового.

## Ключ

```sh
node tools/sign-release.mjs keygen ~/.config/luna/update-key.pem
```

Команда печатает `LUNA_UPDATE_PUBLIC_KEY=<hex>`, создаёт приватный ключ
`~/.config/luna/update-key.pem` (права `0600`) и публичный
`~/.config/luna/update-key.pem.pub.pem`. Приватный ключ не коммитится, не
попадает в CI и не копируется на станции.

Проверить ключ и подпись можно без сборки:

```sh
node tools/sign-release.mjs pubkey ~/.config/luna/update-key.pem
node tools/sign-release.mjs verify dist/release/SHA256SUMS \
  ~/.config/luna/update-key.pem.pub.pem
```

## Сборка релиза

Локальный `tools/release.sh` (он исключён из Git) делает всё сам, если задан
путь к ключу:

```sh
LUNA_UPDATE_KEY_FILE=~/.config/luna/update-key.pem tools/release.sh --update
```

Скрипт выводит публичный ключ, собирает станции с
`LUNA_RELEASE_VERSION=<версия>`, добавляет версию в `manifest.json`, включает
`manifest.json` в `SHA256SUMS`, подписывает файл и прикладывает
`SHA256SUMS.sig` к GitHub-релизу.

При ручной сборке ключ и версия передаются переменными окружения:

```sh
LUNA_UPDATE_PUBLIC_KEY=<hex> LUNA_RELEASE_VERSION=0.2.36 \
  cargo build --release --target aarch64-unknown-linux-musl \
  --manifest-path stations/yandexmini/Cargo.toml --bin luna-yandexmini
```

`LUNA_RELEASE_VERSION` важен: `Cargo.toml` не обновляется на каждый релиз
YAM, и без этой переменной станция считала бы текущей версией `0.2.7`.

## Что получается в релизе

| Файл | Содержимое |
| :-- | :-- |
| `manifest.json` | `schema_version`, `version`, список станций с `asset` и `target` |
| `SHA256SUMS` | хеши всех ассетов и строка `manifest.json` |
| `SHA256SUMS.sig` | сырая 64-байтная Ed25519-подпись `SHA256SUMS` |

Updater также принимает подпись в виде 128 hex-символов.

## Что проверяет станция

1. Скачивает `manifest.json`, `SHA256SUMS` и `SHA256SUMS.sig` (без разбора
   манифеста до проверки).
2. Проверяет подпись одним из вшитых ключей.
3. Сверяет хеш `manifest.json` со строкой в подписанном `SHA256SUMS`.
4. Требует `version` и сравнивает её с версией сборки: равная или меньшая
   версия пропускается.
5. Сверяет хеш своего бинарника и скачанного ассета с `SHA256SUMS`.

Любая ошибка (нет подписи, неверный ключ, старый релиз, неизвестный `target`)
оставляет станцию на текущей версии и пишет предупреждение в лог.

## Сборка без ключа

Если при сборке не задан `LUNA_UPDATE_PUBLIC_KEY`, в бинарнике нет ключа и
автообновление отключено: скачивать и запускать неподписанный код нельзя.
Это касается и CI-сборок, и локальных debug-сборок. Обновление вручную через
YAM или замену бинарника это не ограничивает.

## Ротация ключа

В сборку можно вшить два ключа:

```sh
LUNA_UPDATE_PUBLIC_KEY=<текущий> \
LUNA_UPDATE_PUBLIC_KEY_NEXT=<следующий> \
LUNA_RELEASE_VERSION=0.2.36 cargo build ...
```

Пока станции не обновились, релизы можно подписывать текущим ключом. Затем
выпускается релиз, подписанный следующим ключом: его принимают и старые
станции (у них есть `NEXT`), и новые. После этого следующий ключ становится
текущим, а `NEXT` очищается.

## Ограничения

- Установки через YAM по-прежнему заменяют файл внутри каталога пакета, и YAM
  продолжает считать старую версию. Отказ от самозамены для YAM-установок —
  отдельная задача (пункт 6 issue #55).
- `POST /api/plugins/registry` пока не требует подписи `index.json` и доверяет
  URL реестра (пункт 7 issue #55).
- Старые релизы без `version` и `SHA256SUMS.sig` больше не устанавливаются
  автоматически: это ожидаемое поведение, а не ошибка сети.
